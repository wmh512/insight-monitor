### P003：git 报 detected dubious ownership
- 日期：2026-10-18
- 现象：普通用户执行 git 命令被拒绝，提示仓库属于 BUILTIN\Administrators
- 根因：之前在管理员 PowerShell 中执行 git init，.git 所有者是 Administrators 组，触发 git safe.directory 安全机制（CVE-2022-24765 修复）

### P004：指纹测试失败——发现 stack 含 new Error 行号
- 日期：2026-10-19
- 现象：两次相同的 window.onerror 调用，指纹不同（'23t7kdr7ay0' vs 'ky8q6fdrd3'）
- 排查过程：
  1) 先怀疑 cyrb53 实现 → 用相同字符串直测，输出稳定，排除算法问题
  2) 对比两次的指纹输入 → 发现 stack 第一帧行号不同（测试代码第 70 行 vs 第 71 行）
  3) 顿悟：new Error() 的 stack 顶帧记录的是创建位置的行号，分两行创建两个 Error 堆栈必然不同
- 根因：指纹输入包含堆栈，堆栈包含 new Error() 所在行号
- 解决方案：测试复用同一个 Error 对象；同时确认生产环境无此问题——真实运行时错误的堆栈顶帧是抛出位置，同一处代码每次抛出的堆栈一致
- 衍生认知：这个失败恰好证明了指纹 v2（P1）的必要性——代码热修复导致行号漂移时，同一 issue 的指纹会变化、聚合失效，v2 需要做堆栈归一化（抹行号、保留函数名和文件名）
- 量化结果：测试修复后 24 条全绿；指纹稳定性假设得到验证
- 复盘：
  - 简述："一个测试失败让我发现堆栈里藏着创建行号，理解了指纹稳定性的边界，也验证了指纹算法 v2 的设计必要性"
  - 详版：从失败现象 → 排除算法 → 定位堆栈行号 → 区分测试环境与生产环境 → 推导出 v2 演进方向（讲清"测试驱动的设计验证"）

### P005：测试微任务时序没等够导致断言失败
- 日期：2026-10-22
- 现象：queue.test.ts 两条失败——"fetch 调用次数 1 而非 2"、"localStorage 为空"
- 排查过程：
  1) 先怀疑队列逻辑有 bug → 但 fetch 确实被调用了，生产代码没问题
  2) 单步分析 Promise 链：fetch → 传输层 then/catch → 队列 then，共 3 个微任务 tick
  3) 测试只 await 1-2 次，第三张多米诺还没倒就去断言了
- 根因：await Promise.resolve() 只等一个微任务 tick，不够整条链走完
- 解决方案：写 flushPromises() 助手，等 5 个 tick 兜底
- 复盘：简述——"测试里等 Promise 链不能数着 await 的次数猜，要么等足 tick，要么用事件精确控制，这是 flaky 测试的常见根因"

### P006：全局替换自我污染导致栈溢出
- 日期：2026-10-22

### P007：sendBeacon 投递成功但服务端并未收到
- 日期：2026-10-22
- 现象：demo 控制台显示"投递成功/本批发送成功"，但 Network 面板显示 POST net::ERR_CONNECTION_REFUSED（服务端未启动）
- 根因：sendBeacon 返回值只代表浏览器接受投递（入队），不保证服务端收到——它的设计目标就是"发射后不管"

- 演进方向：① 文档声明该限制；② 需要可靠投递时改用 fetch（可感知成败 + keepalive）；③ 生产级方案是 ack 对账机制
- 复盘：简述——"demo 实测发现 sendBeacon 的成功语义是'浏览器揽收'而非'服务端签收'，这体现了技术选型时对'页面关闭可达性 vs 投递可靠性'的权衡"

### P008：schema.sql 导入时中文 INSERT 失败（客户端编码不匹配）
- 日期：2026-10-23

### P020：PowerShell 重定向污染 mysqldump 导出文件（UTF-16LE）
- 日期：2026-10-24
- 现象：mysqldump 导出后用 < 导入云端，报 ERROR: ASCII '\0' appeared in the statement
- 根因：命令用了 `mysqldump ... > file.sql`——PowerShell 5.1 的 `>` 等于 Out-File，默认以 UTF-16LE 编码写文件，每个 ASCII 字符后多一个 \0 空字节；mysql 客户端按 UTF-8 读取即报错
- 解决方案：改用 mysqldump 自带的 `--result-file=路径`（程序自身以二进制模式写文件，不经 shell 编码转换）
- 衍生认知：与 P008（mysql 客户端 GBK）同家族——**数据经过的每一层都有自己的默认编码假设，二进制/结构化数据必须用程序原生文件输出，不借道路径的编码**；PowerShell 5.1 的 > 重定向是 UTF-16，cmd 的 > 是 ANSI，bash 的 > 是字节流——同一条命令换个 shell 结果不同
- 复盘：简述——"'把输出写到文件'这个动作，在 Windows 各 shell 里有三种编码含义——涉及数据搬家时，用程序自带的文件参数，别用 shell 重定向"

### P021：.gitignore 的 `.env.*` 规则吞掉配置模板 `.env.example`
- 日期：2026-10-25
- 现象：W9-c 提交时发现 `.env.example` 的修改从不出现在 git status；`git ls-files` 证实它**从未被跟踪**——仓库里一直没有配置模板，clone 项目的人不知道要配哪些 key
- 根因：.gitignore 第 12 行 `.env.*`（本意忽略 .env.production 等真实配置）的 glob 同时匹配了 `.env.example`；且**被 ignore 的文件连 status 都不显示**，所以静默存在 6 天无人发现
- 解决方案：.gitignore 加否定模式 `!.env.example`（后置规则覆盖前置规则）+ `git add -f` 强推入历史
- 衍生认知：① gitignore 的 glob 要脑补一遍"会误伤什么"——`.env.*` 误伤 `.env.example` 是经典案例，否定模式 `!` 是标准解药；② 被 ignore 的文件是隐形的——"我没提交过它"和"它被悄悄挡住了"在 status 上看不出区别，要 `ls-files`/`check-ignore` 才能证伪；③ 与 P009/P016/P017 同家族：工具的默认行为会改变你看到的事实，权威验证是唯一真相
- 复盘：简述——"忽略规则的误伤是静默的——被挡的文件连'我存在'都喊不出来；定期审计'我以为进了仓库的东西'，用 check-ignore 和 ls-files，别靠感觉"

### P022：scp 多源文件平铺进同一目录，跨目录上传静默走错房间
- 日期：2026-10-25
- 现象：W9-c 发版后云上告警不触发——grep 证实 reportController.js 是旧版，而 config.js/notifier.js 都是新版
- 根因：`scp a.js b/controllers/c.js root@IP:.../src/` —— **scp 多源语义是所有源文件平铺进同一个目标目录**，c.js 落到了 src/ 根下而非 src/controllers/；旧版控制器原封不动地在岗，notifier 从未被调用
- 解决方案：`mv` 把迷路文件搬回正确目录 + pm2 restart --update-env
- 衍生认知：① 跨目录的多文件上传必须"一个源一条命令"（或先本地打包 tar 再单传解包）；② "传了"≠"传对地方"——发版验证要看目标路径的内容（grep/ls），不能只看 scp 没报错；③ 与 P011/P013 同家族：批量操作的语义要想一遍，提交/上传前审查是最后一道闸
- 复盘：简述——"多文件传输的语义是'全部进一个门'——跨目录时一条源一条命令；上传成功的标准是目标路径里躺着对的内容，不是 scp 没红字"
