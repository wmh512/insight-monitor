### P001：Vite 8 构建报 Failed to load transformWithEsbuild
- 日期：2026-10-18
- 现象：`pnpm sdk:build` 失败，报错 `transformWithEsbuild deprecated, Cannot find package 'esbuild'`
- 环境：Node 24.19.0 / pnpm 12.14.0 / vite 8.3.4（rolldown-vite）
- 排查过程：
  1) 报错明确指向 esbuild 缺失，排除自身配置问题
  2) 查 Vite 8 迁移文档：rolldown-vite 不再内置 esbuild，transformWithEsbuild 需显式依赖
  3) 同时发现 pnpm 12 不再读 package.json 的 pnpm 字段
- 根因：工具链大版本升级带来的依赖分离
- 解决方案：sdk 包单独安装 esbuild；onlyBuiltDependencies 迁至 pnpm-workspace.yaml
- 量化结果：build 从失败到 103ms 完成
- 关联 commit：build: 接入工程依赖链
- 复盘：（待补充）

### P002：pnpm approve-builds 交互界面误操作
- 日期：2026-10-18
- 现象：连续两次直接回车，esbuild 被标记为不批准构建脚本
- 排查：输出显示 "added to allowBuilds with value false" 意识到未选择；第二次运行提示 no packages awaiting approval
- 根因：交互式 TUI 需要空格选中再回车，直接回车等于全部拒绝
- 解决方案：手动修改 pnpm-workspace.yaml `allowBuilds.esbuild: false → true`
- 量化结果：警告消除，esbuild postinstall 正常执行
- 复盘：简述——"交互式配置工具要先看清操作说明；配置文件比交互界面更可控，出问题能直接改"

### P003：git 报 detected dubious ownership
- 日期：2026-10-18
- 现象：普通用户执行 git 命令被拒绝，提示仓库属于 BUILTIN\Administrators
- 根因：之前在管理员 PowerShell 中执行 git init，.git 所有者是 Administrators 组，触发 git safe.directory 安全机制（CVE-2022-24765 修复）
- 解决方案：`git config --global --add safe.directory <项目路径>`
- 教训：git 与项目操作全程使用普通权限窗口；管理员窗口只用于全局安装
- 复盘：简述——"Windows 下混用管理员/普通窗口会导致 .git 所有权混乱，触发 git 安全机制；用 safe.directory 显式信任路径解决，根因是规范窗口使用"

### P004：指纹测试失败——发现 stack 含 new Error 行号
- 日期：2026-10-19
- 现象：两次相同的 window.onerror 调用，指纹不同（'23t7kdr7ay0' vs 'ky8q6fdrd3'）
- 排查过程：
  1) 先怀疑 cyrb53 实现 → 用相同字符串直测，输出稳定，排除算法问题
  2) 对比两次的指纹输入 → 发现 stack 第一帧行号不同（测试代码第 70 行 vs 第 71 行）
  3) 顿悟：new Error() 的 stack 顶帧记录的是创建位置的行号，分两行创建两个 Error 堆栈必然不同
- 根因：指纹输入包含堆栈，堆栈包含 new Error() 所在行号
- 解决方案：测试复用同一个 Error 对象；同时确认生产环境无此问题——真实运行时错误的堆栈顶帧是抛出位置，同一处代码每次抛出的堆栈一致
- 衍生认知：这个失败恰好证明了指纹 v2（P1）的必要性——代码热修复导致行号漂移时，同一 issue 的指纹会变化、聚合失效，v2 需要做堆栈归一化（抹行号、保留函数名和文件名）
- 量化结果：测试修复后 24 条全绿；指纹稳定性假设得到验证
- 复盘：
  - 简述："一个测试失败让我发现堆栈里藏着创建行号，理解了指纹稳定性的边界，也验证了指纹算法 v2 的设计必要性"
  - 详版：从失败现象 → 排除算法 → 定位堆栈行号 → 区分测试环境与生产环境 → 推导出 v2 演进方向（讲清"测试驱动的设计验证"）

### P005：测试微任务时序没等够导致断言失败
- 日期：2026-10-22
- 现象：queue.test.ts 两条失败——"fetch 调用次数 1 而非 2"、"localStorage 为空"
- 排查过程：
  1) 先怀疑队列逻辑有 bug → 但 fetch 确实被调用了，生产代码没问题
  2) 单步分析 Promise 链：fetch → 传输层 then/catch → 队列 then，共 3 个微任务 tick
  3) 测试只 await 1-2 次，第三张多米诺还没倒就去断言了
- 根因：await Promise.resolve() 只等一个微任务 tick，不够整条链走完
- 解决方案：写 flushPromises() 助手，等 5 个 tick 兜底
- 复盘：简述——"测试里等 Promise 链不能数着 await 的次数猜，要么等足 tick，要么用事件精确控制，这是 flaky 测试的常见根因"

### P006：全局替换自我污染导致栈溢出
- 日期：2026-10-22
- 现象：替换后 RangeError: Maximum call stack size exceeded
- 根因：Ctrl+H 全部替换时，替换文本与被替换文本同源，助手函数被换成了递归自调
- 解决方案：助手函数体内改回 await Promise.resolve()
- 教训：全局替换后必须检查"替换文本是否包含被替换文本"；任何批量操作后立刻回归测试
- 复盘：简述——"批量重构后必须回归验证，这类'改 A 坏 B'的问题靠测试网兜底"

### P007：sendBeacon 投递成功但服务端并未收到
- 日期：2026-10-22
- 现象：demo 控制台显示"投递成功/本批发送成功"，但 Network 面板显示 POST net::ERR_CONNECTION_REFUSED（服务端未启动）
- 根因：sendBeacon 返回值只代表浏览器接受投递（入队），不保证服务端收到——它的设计目标就是"发射后不管"
- 影响：服务端宕机时，走 sendBeacon 路径的数据静默丢失，队列的失败重试形同虚设（sendBeacon 从不返回 false）
- 演进方向：① 文档声明该限制；② 需要可靠投递时改用 fetch（可感知成败 + keepalive）；③ 生产级方案是 ack 对账机制
- 复盘：简述——"demo 实测发现 sendBeacon 的成功语义是'浏览器揽收'而非'服务端签收'，这体现了技术选型时对'页面关闭可达性 vs 投递可靠性'的权衡"

### P008：schema.sql 导入时中文 INSERT 失败（客户端编码不匹配）
- 日期：2026-10-23
- 现象：source 执行 schema.sql，三张表建成，但 INSERT 测试数据报 ERROR 1366 Incorrect string value，SELECT 为空
- 根因：文件是 UTF-8，Windows mysql 客户端连接默认 GBK，中文在两种编码间转手变形，MySQL 拒绝接收
- 解决方案：测试数据改用英文插入（联测内容不影响功能）
- 衍生认知：同一个坑会在服务端再现——mysql2 连接池必须显式 charset: 'utf8mb4'，否则 SDK 上报的中文错误信息入库全是 ???。客户端踩的坑，成了服务端配置的提前依据
- 复盘：简述——"编码问题的根因不在某一端，而在'两端说话方式不一致'；解法是显式声明 charset，而不是碰运气"

### P009：pnpm 安装"假成功"——毫秒级耗时
- 日期：2026-10-23
- 现象：pnpm --filter @insight/server add koa ... 显示 Done in 23ms，之后 import 找不到模块
- 排查：对比历史安装耗时（13.8s / 39.6s / 2.1s），毫秒级不可能完成下载；检查发现 packages/server 下没有 package.json，--filter 匹配不到任何包，静默跳过不报错
- 解决方案：先建 package.json（name: @insight/server），重新安装，2.1s +49 包，真成功
- 教训：工具返回成功 ≠ 真成功——用耗时、输出数据量、产物存在性交叉验证；--filter 匹配不到包时 pnpm 静默跳过，是最隐蔽的陷阱
- 复盘：简述——"对工具输出保持警觉：进度条、耗时、产物三者对不上，就是在骗你"

### P010：git 命令在非项目目录执行（管理员窗口默认 System32）
- 日期：2026-10-23
- 现象：git checkout/add/status 三条全部 fatal: not a git repository
- 根因：管理员 PowerShell 打开时默认停在 C:\windows\system32，git 在那里找不到仓库（与 P003 同根源：管理员窗口）
- 解决方案：先 cd 到项目目录再执行
- 教训：git/项目命令只用普通 PowerShell 窗口；任何窗口开工第一件事是确认提示符在项目目录
- 复盘：简述——"同一类环境问题反复踩，说明习惯没养成——把'窗口类型+当前目录'设为执行命令前的固定检查项"
